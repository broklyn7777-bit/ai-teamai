# 编码风格

> 本文档定义通用编码原则。语言专用规则在 `java/`、`typescript/`、`python/` 目录下，是对通用规则的补充和细化。**冲突时以语言专用规则为准。**

## 简洁优先

> 用最少代码解决问题，不做任何预判性设计。

- **零过度设计**：不实现需求以外的功能，不为"未来可能的场景"写代码。
- **长期可演进**：最简实现的结构必须能长期演进，不接受注定推倒重来的权宜方案。
- **拒绝抽象**：单次使用的代码不做封装；不添加未被要求的"灵活性"、配置与间接层。
- **极简主义**：若本可 50 行实现却写了 200 行，必须重写。
- **自我检验**：资深工程师是否会觉得这段代码过度复杂？如果是，简化它。

## 精准修改

> 只修改必需内容，只清理自身产生的冗余代码。

- **最小侵入**：不"优化"相邻代码、注释或格式；不重构没问题的逻辑。
- **尊重现状**：遵循项目现有风格，即便你有不同写法。
- **死代码处理**：发现无关死代码只提示不删除；仅删除因你的改动而失效的导入或变量。
- **检验标准**：Diff 中的每一行修改都应能直接追溯到用户需求。

## 干净切换（不留兼容债）

> 删除本次改动废弃的路径，不新增兼容层、降级方案或迁移逻辑。

- **删除范围**：仅限本次改动触及或废弃的路径；同一改动内更新所有调用方，不留 shim/别名。
- **无关的兼容代码**：只提示不删除（与「精准修改」一致）。
- **唯一例外**：存在明确外部消费者（对外发布的 API/SDK、跨团队协议、持久化数据格式）时可保留兼容层，须在代码中注明理由和下线时间。

## 编码前先思考

> 不随意假设，不掩盖困惑，明确权衡方案。

- **清晰说明假设**：如有不确定，立即停止并提问。
- **列出多种理解**：若需求有歧义，列出所有可能性，不暗自选定。
- **主动提出简化**：若存在更简洁的方案，主动建议。
- **先研究再设计**：方案提出前，先调查成熟产品如何解决相同问题，采用经过验证的模式。
- **拒绝模糊**：若指令不清晰，明确指出困惑点。

## 目标驱动执行

> 定义成功标准，循环验证直至通过。

- **可验证目标**：
  - "添加校验" → "编写测试用例并使其通过"
  - "修复 Bug" → "编写复现脚本并使其通过"
- **多步计划**：`[步骤] → 验证：[检查项]`
- **分层构建**：从端到端可运行的最小版本开始，在可用产品上逐层增加能力，不用未完成的复杂系统替代已运行的产品。
- **拒绝模糊成功**：严禁使用"让它正常运行"作为完成标准，必须提供具体的验证证据（测试日志、截图等）。

## 依赖选择

- **优先现有依赖**：先穷尽项目已有依赖的能力；未查文档和类型定义前，不武断认定某库不支持所需能力。
- **次选成熟库**：现有依赖确实无法满足，且成熟维护良好的库能显著降低复杂度时，才引入新依赖并说明理由。
- **禁止重复造轮子**：无明确理由，不手写已有库覆盖的功能。

## 不可变性（关键）

始终创建新对象，绝不改变现有对象：

```
// 伪代码
WRONG:  modify(original, field, value) → 原地修改 original
CORRECT: update(original, field, value) → 返回包含更改的新副本
```

理由：不可变数据可以防止隐藏的副作用，使调试更容易，并支持安全的并发。

## 文件组织

多个小文件 > 少数大文件：

* 高内聚，低耦合
* 通常 200-400 行，最多 800 行
* 从大型模块中提取实用工具
* 按功能/领域组织，而不是按类型组织

## 错误处理

始终全面处理错误：

* 在每个层级明确处理错误
* 在面向用户的代码中提供用户友好的错误消息
* 在服务器端记录详细的错误上下文
* 绝不默默地忽略错误

## 输入验证

始终在系统边界处进行验证：

* 在处理前验证所有用户输入
* 在可用时使用基于模式的验证
* 快速失败并提供清晰的错误消息
* 绝不信任外部数据（API 响应、用户输入、文件内容）

## 完成标准

任务只有在满足以下所有条件时方可结束：

* [ ] 目标实现：符合简洁与精准要求
* [ ] 验证通过：提供了测试通过证据或运行截图
* [ ] 无过度设计：代码差异中无无关改动
* [ ] 风险透明：明确告知遗留问题或副作用

## 代码 Review 准则

按以下顺序审查：

* [ ] 功能正确：覆盖主路径，未验证的优先指出
* [ ] 方案合理：大改动替代方案先确认再实施
* [ ] 无过度问题：无过度设计、过度防御、过度嵌套
* [ ] 测试有价值：保留验证真实行为的测试，清理低价值测试

## 代码质量检查清单

在标记工作完成之前：

* [ ] 代码可读且命名良好
* [ ] 函数短小（<50 行）
* [ ] 文件专注（<800 行）
* [ ] 没有深度嵌套（>4 层）
* [ ] 正确的错误处理
* [ ] 没有硬编码的值（使用常量或配置）
* [ ] 没有突变（使用不可变模式）
