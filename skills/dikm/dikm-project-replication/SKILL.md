# 项目功能复制技能指南

系统性地将源项目功能复制到技术栈不同的目标项目。五阶段交付：先做功能差距分析，再逐模块完成"链路分析→方案设计→任务拆解→TDD实现→完成标记"的循环，最后整体验证。

## 核心原则

1. **代码实证** — 所有分析从两个项目的真实代码出发，不靠文档猜测、不做主观假设
2. **架构合理性优先** — 源项目架构不一定合理。复制前先问"这个设计在目标项目中说得通吗"，不盲目搬运
3. **适配而非翻译** — 概念映射到目标技术栈的惯用方式，不做 1:1 代码翻译
4. **复用优先** — 充分利用目标项目已有的认证、数据库、中间件、组件库。新功能嵌入现有架构，不另起炉灶
5. **极简主义** — 只构建当前需要的功能。非核心任务明确放入后续规划，不为"未来可能的场景"写代码

---

## 四阶段工作流

```
Phase 0              Phase 1                   Phase 2          Phase 3
功能差距分析 → 逐模块复刻循环（重复执行） → 整体验证Gate → [完成]
  [Gate]            分析→方案→任务→TDD→标记      [Gate]
```

每个 Phase 结束有明确 Gate 条件，**未通过不进入下一阶段**。

### Phase 0：功能差距分析

**目标**：明确"复刻什么、跳过什么"，输出结构化差距分析文档。

#### 0.1 全量功能盘点

从源项目真实代码出发（不是文档），逐功能点对比：

| 字段 | 说明 |
|------|------|
| 功能名 | 一句话描述 |
| 状态 | ✅ 已实现 / ⚠️ 部分实现 / ❌ 缺失 |
| 源项目实现位置 | 关键文件/表/API |
| 目标项目现状 | 已有代码 / 基础设施 / 完全没有 |
| 差距 | 无 / 需适配 / 需复刻 / 后续考虑 |

#### 0.2 功能聚类

将缺失功能按**业务关联性**聚类成集群，每个集群内部功能有强依赖关系：

```
集群 1: [名称]（高优先级）
  功能A ←→ 功能B ←→ 功能C
    ↓
  前端落地：[简述前端呈现]

集群 2: [名称]（中优先级）
  ...
```

#### 0.3 优先级排序

| 优先级 | 标准 | 说明 |
|--------|------|------|
| 🔴 P0 | 核心基础能力 | 缺少会导致功能不完整或有 bug |
| 🟡 P1 | 重要增强 | 提升体验但不阻塞核心流程 |
| 🟢 P2 | 锦上添花 | 可延后或跳过 |
| ⚪ 后续 | 需要较大前置工作 | 明确不在本次范围 |

#### 0.4 确认复刻范围

让用户明确确认本次复刻的功能列表（按集群或优先级选择）。

**输出**：功能差距分析文档。严格按 [功能差距分析模板](references/feature-gap-template.md) 生成。

**Gate 条件**：
- [ ] 功能清单逐项对比完成（含状态标注）
- [ ] 缺失功能已聚类分组
- [ ] 优先级已排序
- [ ] 用户已确认本次复刻范围

### Phase 1：逐模块复刻循环

**目标**：对确认复刻的每个功能模块，完成完整的"分析→设计→任务→实现→标记"循环。

> **核心原则：一次只处理一个模块，完成后再进入下一个。**

对 Phase 0 确认的每个功能模块（按优先级排序），依次执行以下 5 步：

#### Step 1：源项目全链路分析

从源项目真实代码出发，追踪该模块的完整调用链。

**三维分析**：

| 维度 | 分析内容 | 重点 |
|------|---------|------|
| **表结构** | 实体关系、核心字段、约束索引 | 决定目标项目怎么建表 |
| **代码链路** | 入口→中间件→Service→Repository→DB→异步副作用 | 理解"怎么做一件事" |
| **前端交互** | 页面路由、数据流、交互事件链 | 理解用户操作意图 |

**分析方法**：
- 从 API 入口或路由定义读代码，沿调用链向下追踪
- 对每个函数问"它做什么、调了谁、返回什么"
- 画出一条核心功能的完整时序图
- 参考 [架构分析模板](references/architecture-analysis.md)

**输出**：链路分析文档。参考 [源项目链路分析模板](references/source-chain-template.md)。

#### Step 2：目标项目链路分析

分析目标项目中与该模块相关的现有实现和基础设施。

| 分析项 | 内容 |
|--------|------|
| **已有实现** | 目标项目中已有哪些相关功能？代码在哪？ |
| **基础设施** | 认证/DB/中间件/组件库可复用哪些？ |
| **架构约束** | 目标项目有哪些不可违背的架构约定？（读 CLAUDE.md / ARCHITECTURE.md） |
| **差距清单** | 需要新建 / 扩展 / 适配的组件列表 |

**输出**：目标项目链路分析文档。参考 [目标项目链路分析模板](references/target-chain-template.md)。

#### Step 3：方案架构评估

基于 Step 1-2 的分析，设计适配方案。**此步骤必须先与用户对齐再执行。**

##### 3.1 架构合理性校验

对源项目的每个关键设计决策逐一校验：

| 校验问题 | 判断标准 |
|---------|---------|
| 这个设计解决的核心问题是什么？ | 问题在目标项目中不存在 → 设计可能不需要 |
| 目标项目有更自然的方式解决同一问题吗？ | 有 → 用目标项目方式；没有 → 考虑引入 |
| 引入这个设计会破坏目标项目哪些一致性？ | 破坏 > 收益 → 拒绝 |
| 团队能否维护这个设计？ | 超出认知 → 简化或跳过 |

每个设计决策记录到 [适配决策日志](references/decision-log.md)。

##### 3.2 架构方案设计

输出包含：
- **数据模型映射**：源表 → 目标表（新建/扩展/复用），字段对应关系
- **API 设计**：端点列表、请求/响应格式、与已有 API 的风格一致性
- **前端方案**：页面结构、组件选择、交互设计（适配目标项目组件库）
- **架构流程图**：新模块在目标项目中的完整调用链路

##### 3.3 方案对齐（不可跳过）

> ⚠️ **铁律：方案存在任何疑问，必须先与用户对齐确认后再继续。**
> - 列出所有不确定点，逐一确认
> - 有多个候选方案时，列出各方案优劣，让用户选择
> - 不得跳过此步直接执行

**输出**：架构方案文档（含流程图）。

#### Step 4：任务拆解

##### 4.1 核心 vs 非核心分类

| 分类 | 标准 | 处理 |
|------|------|------|
| **核心任务** | 当前模块必须完成 | 进入 Step 5 执行 |
| **非核心任务** | 增强体验但非必须 | 整理为后续规划文档 |

##### 4.2 核心任务排序

按依赖顺序排列，每个任务标注：

| # | 任务 | 验证标准 | 依赖 |
|---|------|---------|------|
| 1.x | 数据库 Schema（表/字段/迁移） | 迁移成功、约束生效 | 无 |
| 1.x+1 | 后端 API（端点/逻辑） | 接口可调通、数据正确 | 1.x |
| 1.x+2 | 前端实现（组件/交互） | 页面可操作、数据展示正确 | 1.x+1 |
| 1.x+3 | 联调验证 | 端到端走通 | 1.x+2 |

##### 4.3 后续规划文档

非核心任务整理为独立文档，包含：
- 任务名称 + 简要描述
- 预估复杂度（低/中/高）
- 前置依赖
- 推荐执行时机

**输出**：核心任务清单 + 后续规划文档。

#### Step 5：TDD 实现

##### 5.1 执行循环

按任务清单顺序，每个任务遵循 **RED → GREEN → REFACTOR**：

```
┌─── 每个任务 ───────────────────────────────────┐
│                                                  │
│  🔴 RED: 写失败测试                               │
│    · 定义预期行为（输入→输出/状态变化）             │
│    · 测试必须失败（不写测试后实现）                 │
│    · 包含正常路径 + 关键边界                       │
│                                                  │
│  🟢 GREEN: 写最小实现                             │
│    · 只写让测试通过的代码                          │
│    · 不做额外抽象、不处理未测试的场景               │
│                                                  │
│  🔵 REFACTOR: 重构                               │
│    · 消除重复，改善命名                            │
│    · 确保所有测试仍然通过                          │
│    · 补充遗漏的边界测试                            │
│                                                  │
│  ✅ 验收:                                        │
│    · 相关测试全部通过                              │
│    · 代码符合目标项目规范（lint/format）           │
│    · git commit（不得积攒）                        │
│    · 标记完成：任务清单中勾选 ☑️                  │
│                                                  │
└──────────────────────────────────────────────────┘
```

##### 5.2 关键约束

| 约束 | 说明 |
|------|------|
| **字段评估铁律** | 对目标项目已有表新增字段前：列出使用场景 → 评估替代方案 → 确认影响范围。三项通过才能新增 |
| **最小侵入** | 不"优化"无关代码，匹配目标项目风格 |
| **适配原则** | 用目标技术栈惯用方式实现，不 1:1 翻译源项目代码 |
| **每任务一提交** | 每个任务完成后立即 commit + 标记，不积攒 |
| **测试位置** | 遵循目标项目测试目录规范 |

##### 5.3 垂直切片验证

每个任务完成后，验证其所在的垂直切片（DB → API → UI）是否走通：

参考 [垂直切片测试指南](references/testing-guide.md)。

#### 模块完成标记

当模块的所有核心任务完成后：

- [ ] 模块任务清单全部 ☑️
- [ ] 本模块所有测试通过
- [ ] 本模块代码已 commit
- [ ] 适配决策已记录

**→ 进入下一个功能模块，回到 Step 1。**
**→ 所有模块完成后，进入 Phase 2。**

详见 [逐模块复刻指南](references/module-loop.md)。

---

### Phase 2：整体验证

**目标**：确保所有复刻模块协同工作，无回归。

| 验证项 | 方法 |
|--------|------|
| 全量测试 | 跑所有单元/集成/E2E 测试，确保无回归 |
| Lint + 类型检查 | 代码规范检查通过 |
| 端到端主流程 | 核心场景端到端走通 |
| 文档同步 | 更新 changelog + 相关文档 |

**Gate 条件**：
- [ ] 核心功能端到端验证通过
- [ ] 所有测试通过 + lint 通过
- [ ] 非核心任务已有明确的后续规划文档
- [ ] changelog 已更新

## 常见陷阱

| 陷阱 | 解决方案 |
|------|---------|
| 盲目搬运源项目架构 | Phase 0 差距分析 + 每模块 Step 3 架构合理性校验 |
| 凭假设做设计 | 两个项目都必须读实际代码 |
| 横向铺开（先做所有 DB 再做所有 API） | 垂直切片：每个功能从 DB 做到 UI |
| 跳过 TDD 直接写实现 | Phase 1 Step 5 强制执行 RED → GREEN → REFACTOR |
| 方案有疑问就急着写代码 | Step 3 方案对齐检查点（不可跳过） |
| 主链路没通就开始补功能 | 模块完成 Gate 未过不进下一模块 |
| 盲目给已有表加字段 | 字段评估铁律 |
| 非核心任务混入核心流程 | Step 4 明确分类，非核心进后续规划文档 |
| 1:1 代码翻译 | 映射概念，不翻译代码行 |
