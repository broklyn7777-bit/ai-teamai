# 逐模块复刻循环指南

Phase 1 的详细操作指南。对每个功能模块，完成"分析→方案→任务→TDD→标记"的完整循环。

---

## 循环总览

```
模块 M（按优先级排序）
  │
  ├─ Step 1: 源项目全链路分析 → 输出 {chain-doc}
  │    └─ 三维分析：表结构 + 代码链路 + 前端交互
  │
  ├─ Step 2: 目标项目链路分析 → 输出 {target-doc}
  │    └─ 已有实现 + 基础设施 + 架构约束 + 差距清单
  │
  ├─ Step 3: 方案架构评估 → 输出 {plan-doc}
  │    ├─ 3.1 架构合理性校验
  │    ├─ 3.2 架构方案设计
  │    └─ 3.3 方案对齐 ⚠️ 有疑问必须先对齐
  │
  ├─ Step 4: 任务拆解
  │    ├─ 核心任务清单（进入 Step 5）
  │    └─ 非核心任务 → {future-doc} 后续规划文档
  │
  ├─ Step 5: TDD 实现
  │    └─ 每个任务: RED → GREEN → REFACTOR → commit → ☑️
  │
  └─ 模块完成标记 → 进入下一个模块或 Phase 2
```

---

## Step 1: 源项目全链路分析

### 分析目标

理解源项目"怎么做一件事"，提取可迁移的设计意图。

### 操作步骤

1. **定位入口**：从 API 路由或前端页面入口开始
2. **追踪调用链**：入口 → 中间件 → Service → Repository → DB
3. **提取关键信息**：

| 分析项 | 具体内容 |
|--------|---------|
| 调用链 | Controller → Service → Repository → SQL |
| 数据模型 | 核心表、字段、关系、约束 |
| 中间件链 | 认证、权限、日志的顺序和行为 |
| 数据转换 | DTO/VO 的转换逻辑 |
| 异步链路 | 事件发布、消息队列、定时任务 |
| 错误传播 | 每层如何捕获/转换/传播错误 |
| 前端交互 | 页面 → API → 数据 的依赖关系 |

### 关键文件索引

为分析结果建立文件索引，便于后续定位：

| 层 | 文件 | 核心职责 |
|---|------|---------|
| 路由 | {路径} | 入口 + 参数校验 |
| Handler/Controller | {路径} | 请求处理 |
| Service | {路径} | 业务逻辑 |
| Repository/DAO | {路径} | 数据访问 |
| Model/Entity | {路径} | 数据模型 |
| 前端页面 | {路径} | UI 交互 |
| 前端 API | {路径} | API 调用封装 |

### 输出格式

严格按 [源项目链路分析模板](source-chain-template.md) 输出，包含：
- 项目架构概览（目录树）
- 核心功能链路（时序图 + 代码片段 + 调用链）
- 数据模型（表结构 + 关系）
- 中间件/插件链
- 异步/副作用链路
- 前端交互链路
- 端到端流程全景图

## Step 2: 目标项目链路分析

### 分析目标

理解目标项目中与当前模块相关的现有实现，确定复用/扩展/新建的边界。

### 操作步骤

1. **读项目架构文档**：先读 CLAUDE.md / ARCHITECTURE.md 了解架构约束
2. **盘点已有实现**：搜索与当前模块相关的代码
3. **评估基础设施**：认证/DB/中间件/组件库可复用哪些

### 输出格式

严格按 [目标项目链路分析模板](target-chain-template.md) 输出，包含：
- 架构全景图
- 相关现有实现盘点
- 基础设施评估
- 核心组件链路
- 数据模型现状
- API/路由现状
- 前端现状
- **差距清单**（可复用 / 需扩展 / 需新建 / 不可违背的约束）
- 适配方案输入

## Step 3: 方案架构评估

### 3.1 架构合理性校验

对源项目每个关键设计决策逐一校验：

| 校验问题 | 判断 |
|---------|------|
| 这个设计解决的核心问题是什么？ | {问题描述} |
| 目标项目有更自然的方式吗？ | {有/没有，方案是...} |
| 引入会破坏目标项目一致性吗？ | {破坏点 / 无破坏} |
| 团队能否维护？ | {能/不能，理由} |

记录到 [适配决策日志](decision-log.md)。

### 3.2 架构方案设计

输出内容：

```markdown
## 数据模型映射
| 源表 | 目标表 | 策略 | 字段对应 |
|------|--------|------|---------|
| source_table | target_table | 新建/扩展/复用 | ... |

## API 设计
| 端点 | 方法 | 说明 | 与已有 API 的一致性 |
|------|------|------|-------------------|

## 前端方案
- 页面结构：...
- 组件选择：使用目标项目组件库的 ...
- 交互设计：...

## 架构流程图
[ASCII 图或 Mermaid]
```

### 3.3 方案对齐（铁律）

> ⚠️ **方案存在任何疑问，必须先与用户对齐确认后再继续。**

**必须对齐的内容**：
- 不确定的设计决策
- 有多个候选方案的选择题
- 与目标项目现有模式不一致的地方
- 需要引入的新概念或新依赖

**对齐方式**：
1. 列出所有不确定点
2. 对每个不确定点列出候选方案 + 优劣
3. 等待用户明确选择
4. 记录最终决策

## Step 4: 任务拆解

### 核心 vs 非核心分类

| 分类 | 标准 | 处理 |
|------|------|------|
| **核心任务** | 当前模块必须完成，缺少则功能不完整 | 进入 Step 5 执行 |
| **非核心任务** | 增强体验但非必须，可延后 | 整理为后续规划文档 |

## Step 5: TDD 实现

### 执行循环

每个任务按以下顺序执行：

#### 🔴 RED — 写失败测试

1. 根据任务的验证标准，编写测试用例
2. 测试必须覆盖：正常路径 + 关键边界
3. 运行测试 → 确认全部失败（红色）
4. 如果测试通过 → 说明测试没有验证新行为，重写

```python
# 测试命名规范：test_{功能}_{场景}_{预期}
def test_create_issue_with_parent():
    """父子 Issue 创建：子 Issue 应继承父 Issue 的 project_id"""
    # Arrange
    parent = create_issue(project_id=1, title="Parent")
    # Act
    child = create_issue(project_id=None, parent_id=parent.id, title="Child")
    # Assert
    assert child.project_id == 1  # 继承自 parent
    assert child.parent_issue_id == parent.id
```

#### 🟢 GREEN — 写最小实现

1. 只写让测试通过的代码
2. 不做额外抽象
3. 不处理未被测试覆盖的场景
4. 运行测试 → 确认全部通过（绿色）

#### 🔵 REFACTOR — 重构

1. 消除重复代码
2. 改善命名
3. 确保所有测试仍然通过
4. 补充遗漏的边界测试

#### ✅ 验收 — 标记完成

1. 相关测试全部通过
2. lint / format 检查通过
3. `git commit`（不得积攒）
4. 在任务清单中将 ☐ 改为 ☑️
5. 简短记录完成内容

### 字段评估铁律

对目标项目已有表新增字段前，必须完成三项评估：

| 评估项 | 说明 | 不通过的后果 |
|--------|------|------------|
| 使用场景 | 列出所有读写该字段的代码路径 | 仅"可能有用" → 拒绝 |
| 替代方案 | 关联表、计算字段、配置表能否替代 | 可替代 → 拒绝 |
| 影响范围 | 该表被哪些模块使用，影响序列化/迁移/前端 | 影响面过大 → 拒绝 |

## 模块完成检查清单

每个模块完成后，确认以下所有项：

- [ ] 模块任务清单全部 ☑️
- [ ] 本模块所有测试通过（单元 + 集成）
- [ ] 本模块代码已 commit（不积攒）
- [ ] 适配决策已记录到 decision-log.md
- [ ] 非核心任务已整理到后续规划文档
- [ ] 无回归（已有功能未被破坏）

**→ 进入下一个功能模块，回到 Step 1。**
**→ 所有模块完成后，进入 Phase 2（整体验证）。**
